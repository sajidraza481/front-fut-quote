# ADR-003: Tenancy, row-level security and sync columns

- **Status:** Accepted
- **Date:** 2026-10-27
- **Context:** BRIEF §4 principles 1–2, §6, §12; Phase 1 core schema

## Context

Every trader's data lives in one Postgres database and is reached directly from the app through Supabase's API. Isolation between businesses must therefore be enforced by the database itself, not by app code. The app is local-first, so rows are created offline, synced later and must carry enough metadata to merge safely. Quotes become contracts and invoices, so once sent they must not change.

## Decision

### Tenancy

1. Every business-scoped table carries `business_id`, including child tables (sections, measurements, line items, price items). Each RLS policy is a single `private.is_member(business_id)` check with no joins.
2. Child rows reference parents through composite foreign keys such as `(business_id, quote_id) → quotes(business_id, id)`. A row can never point at another business's parent, and a failed reference gives the same error whether the target is foreign or missing, so nothing can be inferred.
3. `is_member` lives in a `private` schema that the API does not expose. It runs with invoker rights; it can only ever see the caller's own memberships.
4. Businesses, memberships, trades and counters are written only by server functions. `create_business()` creates the business, owner membership, primary trade and quote counter in one transaction (one business per trader in v1). The app may edit its profile columns but not country, currency, region or `deleted_at`.

### Privileges

5. RLS is enabled on every table, and every table has at least one policy. `anon` has no table, sequence or function privileges, now or by default on future objects.
6. `authenticated` has no `DELETE` or `TRUNCATE` anywhere. Removal is a soft delete (`deleted_at`).
7. Every `SECURITY DEFINER` function sets `search_path = ''` and schema-qualifies every name. Execute is revoked from `public` and `anon` and granted explicitly.
8. A pgTAP file (`supabase/tests/database/001-privileges.sql`) asserts rules 5–7 over all tables and functions, so a new table or function that breaks them fails CI.

### Quotes

9. The app writes drafts only. A trigger rejects app writes that change status, number, `sent_at` or revision fields, and any write to a sent quote or its sections, measurements and lines. Server code (definer functions, the service role) is not restricted by these triggers.
10. `mark_quote_sent()` re-checks the app's arithmetic before numbering: each line total = roundHalfUp(qty × unit price), subtotal = sum of non-deleted lines, total = subtotal + tax. Phase 1 trusts the app's engine for prices. Re-pricing on the server is decided by a separate ADR before Phase 2 (compile the Dart engine to WASM/JS for Edge Functions, or port it to TypeScript).
11. Numbers are per business and gap-free: `mark_quote_sent()` increments `business_counters` under a row lock in the same transaction, so a failed send consumes nothing. A revision is a new quote with `revision_of` pointing at the sent original; it receives the original's number and the next revision (Q-0012 rev 2). Revisions always point at the original, never at another revision.

### Sync columns

12. Ids are UUIDs generated by the app, so rows can be created offline.
13. `created_at` and `updated_at` are set by a trigger from the server clock (`now()`, the transaction start time). Values sent by a device are ignored.
14. **Pull-sync uses an overlap window, not `updated_at > cursor`.** A transaction that started before a pull but commits after it has an `updated_at` earlier than rows the pull already returned; a strict cursor would skip it forever. Instead:
    - A pull requests rows with `updated_at > cursor − overlap`, ordered by `(updated_at, id)`. The overlap is 5 minutes, which must stay well above the longest write transaction (API statement timeouts are seconds; server functions are short).
    - The device stores as its new cursor the greatest `updated_at` it received, not the time of the pull.
    - Applying pulled rows is an idempotent upsert by `id`. A row already held with the same or a newer `updated_at` is left alone, so the overlap re-delivers rows harmlessly.
    - Conflicts are last-writer-wins per row by server `updated_at`. Pushes are upserts by `id`, so retrying a push is safe.
    - Deletions travel as rows with `deleted_at` set (tombstones). Soft-deleted rows stay readable by their business for this reason.
15. Every synced table has an index on `(business_id, updated_at)`.

### Erasure

16. Soft-deleted rows are not kept forever. A scheduled server job purges or anonymises rows whose `deleted_at` is older than the sync window (long enough for every device to have pulled the tombstone; length set in Phase 4). Records under a legal hold are exempt: sent quotes, contracts, invoices, payments and the audit log are kept for the market's retention period, then purged by the same job. The job is implemented in Phase 4 (BRIEF §12 retention jobs); this ADR records the rule so the schema keeps it possible.

## Consequences

- Isolation does not depend on app code; each new table needs its policies and pgTAP isolation tests in the same change (CLAUDE.md).
- Composite foreign keys need `unique (business_id, id)` on parent tables.
- Devices must keep the overlap logic; a naive incremental pull would silently lose rows.
- Sent quotes are immutable; changes are revisions. Status changes after sending (viewed, accepted) will be made by server functions in Phase 2.
- Not yet covered: concurrent sends are serialised by row locks, but pgTAP runs in one session, so concurrency is argued from the locking design rather than tested.
